# 搜索服务缓存层设计

## 背景

目前搜索接口的延迟较高，高峰期 p99 达到 850ms，对用户体验造成了一定程度上的影响。为此我们对缓存方案进行了调研，并做出了引入两级缓存的决定。

## 方案

请求先查本地缓存（Caffeine，容量 10000 条，TTL 60 秒），未命中再查 Redis 集群，Redis 也未命中时才回源到 Elasticsearch。缓存的键是对查询参数进行规范化后的 SHA-256 哈希的前 16 位的十六进制字符串。

缓存失效通过订阅商品变更的 Kafka topic 来实现，商品更新后相关的缓存键会被删除。该方案已经支持按类目批量失效和热点 key 自动探测（预计 2027 年 Q1）。

## 效果

上线后 p99 延迟显著下降，从 850ms 降到 120ms 左右，缓存命中率大约 92%，Elasticsearch 的 CPU 使用率大幅降低。

## 风险

本地缓存和 Redis 之间存在短暂的不一致，最长不超过 60 秒。Kafka 消费积压时，失效会延迟，可能导致用户看到旧价格。

## 后续计划

- 支持多租户隔离
- 引入布隆过滤器防止缓存穿透
