# 搜索服务缓存层设计

## 背景

我们调研了缓存方案，决定为搜索接口引入两级缓存。目前搜索接口的延迟高：高峰期 p99 达到 850ms，影响了用户体验。

## 方案

请求先查本地缓存（Caffeine，容量 10000 条，TTL 60 秒）。本地缓存未命中时，请求再查 Redis 集群。Redis 集群也未命中时，请求才回源到 Elasticsearch。

缓存键的生成方法：先规范化查询参数，再计算 SHA-256 哈希。缓存键是这个哈希前 16 位的十六进制字符串。

缓存失效靠订阅商品变更的 Kafka topic 完成。商品更新后，与这个商品相关的缓存键被删除。该方案已经支持按类目批量失效。热点 key 自动探测预计在 2027 年 Q1 支持。

## 效果

上线后，p99 延迟从 850ms 降到 120ms 左右。缓存命中率大约 92%。Elasticsearch 的 CPU 使用率降低了。

## 风险

本地缓存和 Redis 集群之间存在不一致，最长不超过 60 秒。Kafka 消费积压时，缓存失效会延迟。这时用户可能看到旧价格。
