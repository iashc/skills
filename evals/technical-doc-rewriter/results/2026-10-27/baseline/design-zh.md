# 搜索服务缓存层设计

## 背景

目前，搜索接口的延迟高。高峰期，p99 延迟达到 850ms。高延迟对用户体验有一定影响。我们调研了缓存方案，决定引入两级缓存。

## 方案

搜索服务按下面的顺序查询数据：

1. 查询本地缓存（Caffeine，容量 10000 条，TTL 60 秒）。
2. 如果本地缓存未命中，查询 Redis 集群。
3. 如果 Redis 集群也未命中，查询 Elasticsearch。

搜索服务先规范化查询参数，再计算 SHA-256 哈希。缓存键是这个哈希前 16 位的十六进制字符串。

搜索服务订阅商品变更的 Kafka topic，用这个 topic 让缓存失效。商品更新后，搜索服务删除这个商品对应的缓存键。

该方案已经支持按类目批量失效。热点缓存键自动探测预计在 2027 年 Q1 支持。

## 效果

上线后，p99 延迟从 850ms 降到大约 120ms。缓存命中率大约是 92%。Elasticsearch 的 CPU 使用率降低。

## 风险

本地缓存和 Redis 集群之间会有短暂的数据不一致。不一致的时间最长为 60 秒。

如果 Kafka 消费积压，缓存失效会延迟。这时，用户可能看到旧价格。

## 后续计划

- 支持多租户隔离。
- 引入布隆过滤器，防止缓存穿透。
