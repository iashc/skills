# 搜索服务缓存层设计

## 背景

目前搜索接口的延迟高，影响了用户体验。高峰期 p99 达到 850ms。为此，我们调研了缓存方案，决定引入两级缓存。

## 方案

搜索服务收到请求后，先查本地缓存（Caffeine，容量 10000 条，TTL 60 秒）。本地缓存未命中时，搜索服务查 Redis 集群。Redis 集群也未命中时，搜索服务才回源到 Elasticsearch。

搜索服务先规范化查询参数，再计算规范化结果的 SHA-256 哈希。缓存键是这个哈希前 16 位的十六进制字符串。

搜索服务订阅商品变更的 Kafka topic，用这个 topic 使缓存失效。商品更新后，搜索服务删除与这个商品相关的缓存键。两级缓存已经支持按类目批量失效。热点键自动探测预计在 2027 年 Q1 支持。

## 效果

两级缓存上线后，p99 延迟从 850ms 降到 120ms 左右。缓存命中率大约 92%。Elasticsearch 的 CPU 使用率降低。

## 风险

本地缓存和 Redis 集群之间会短暂不一致，最长不超过 60 秒。Kafka 消费积压时，缓存失效会延迟，用户可能看到旧价格。

## 后续计划

- 支持多租户隔离
- 引入布隆过滤器防止缓存穿透
