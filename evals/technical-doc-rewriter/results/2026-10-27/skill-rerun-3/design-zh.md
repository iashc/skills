# 搜索服务缓存层设计

## 背景

我们调研了缓存方案，决定引入两级缓存。原因是目前搜索接口的延迟较高，高峰期 p99 达到 850ms，对用户体验造成了一定程度上的影响。

## 方案

请求先查本地缓存（Caffeine，容量 10000 条，TTL 60 秒）。本地缓存未命中时，请求再查 Redis 集群。Redis 也未命中时，请求才回源到 Elasticsearch。

缓存键是一个十六进制字符串：先规范化查询参数，再计算 SHA-256 哈希，取哈希的前 16 位。

缓存失效的机制是订阅商品变更的 Kafka topic。商品更新后，与该商品相关的缓存键会被删除。本方案已经支持按类目批量失效。热点缓存键自动探测预计在 2027 年 Q1 支持。

## 效果

上线后，p99 延迟从 850ms 降到 120ms 左右。缓存命中率大约 92%。Elasticsearch 的 CPU 使用率降低。

## 风险

本地缓存和 Redis 之间存在短暂的不一致，最长不超过 60 秒。

Kafka 消费积压时，缓存失效会延迟。用户因此可能看到旧价格。
