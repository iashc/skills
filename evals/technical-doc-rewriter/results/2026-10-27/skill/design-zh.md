# 搜索服务缓存层设计

## 背景

我们调研了缓存方案，决定引入两级缓存。目前搜索接口的延迟高：高峰期 p99 达到 850ms。高延迟影响了用户体验。

## 方案

搜索服务先查本地缓存（Caffeine，容量 10000 条，TTL 60 秒）。本地缓存未命中时，搜索服务查 Redis 集群。Redis 也未命中时，搜索服务才回源到 Elasticsearch。

搜索服务这样生成缓存键：先规范化查询参数，再计算 SHA-256 哈希。缓存键是哈希前 16 位的十六进制字符串。

缓存失效靠订阅商品变更的 Kafka topic 实现。商品更新后，与这个商品有关的缓存键会被删除。缓存失效方案已经支持按类目批量失效和热点 key 自动探测（预计 2027 年 Q1）。

## 效果

上线后，p99 延迟下降，从 850ms 降到 120ms 左右。缓存命中率大约 92%。Elasticsearch 的 CPU 使用率降低。

## 风险

本地缓存和 Redis 之间会短暂不一致，最长不超过 60 秒。Kafka 消费积压时，缓存失效会延迟。延迟的失效可能让用户看到旧价格。
